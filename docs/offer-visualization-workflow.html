Workflow de visualisation d'une offre

Ce document décrit le chemin complet d'une consultation d'offres, depuis l'écran du frontend jusqu'à la base de données puis au retour complet vers l'interface. Il montre comment la requête est envoyée, filtrée par rôle, autorisée côté backend, puis affichée dans la page des offres.

Étapes détaillées

  1. Le composant page charge les données.
    Le composant OffersPage instancie le hook useOffers(token, onUnauthorized). Le hook déclenche un effet React et appelle getOffers(token, signal).
  2. Le frontend envoie la requête HTTP.
    Le service frontend construit l'URL /api/offers avec le token dans l'en-tête Authorization : 
    fetch(`${API_URL}/offers`, {
  headers: { Authorization: token },
  signal,
});
  3. Le backend reçoit la requête et valide la session.
    La route est montée dans app.ts avec un middleware d'authentification : 
    app.use("/offers", authenticate, createOffersRouter(offersService));
    La route elle-même exige la règle authorize(canListOffers) avant d'exécuter le contrôleur.
  4. La permission dépend du profil utilisateur.
    La règle de visibilité est définie dans le service :
    • admin : voit toutes les offres
    • étudiant : ne voit que les offres publiées
    • contact déposant : ne voit que ses propres offres
    Le code centralise ce filtre avec visibilityFilter(viewer).
  5. Le repository interroge SQLite.
    La requête SQL sélectionne les offres avec les colonnes utiles et les jointures sur companies, academic_years et periods : 
    SELECT o.id, o.title, o.description, o.status,
       o.company_id, c.short_name AS company_short_name,
       o.depositor_contact_id,
       ay.label AS academic_year_label, p.code AS period_code,
       o.created_at, o.updated_at
FROM offers o
JOIN companies c ON c.id = o.company_id
JOIN academic_years ay ON ay.id = o.academic_year_id
JOIN periods p ON p.id = o.period_id
WHERE (@status IS NULL OR o.status = @status)
  AND (@depositorContactId IS NULL OR o.depositor_contact_id = @depositorContactId)
ORDER BY ay.start_date DESC, o.created_at DESC
  6. Le mapper transforme la ligne SQL en objet métier puis en DTO.
    Le repository renvoie des objets DBO. Le service applique toOffer, puis le contrôleur convertit le résultat final avec toOfferDto pour la réponse HTTP.
  7. La réponse HTTP revient au frontend.
    Le frontend appelle readJson(response, isOfferList, "Chargement des offres impossible") pour vérifier le statut HTTP et valider la structure JSON avant de la stocker dans l'état local.
  8. L'interface affiche les offres.
    Le hook met à jour offers et, une fois chargé, la page affiche OfferTable. Si la liste est vide, elle affiche un état vide ; si le serveur renvoie 401, elle déclenche onUnauthorized() et renvoie l'utilisateur à l'écran de connexion.
Point important : la logique de visibilité n'est pas décidée côté navigateur. Elle est calculée dans le backend, à partir du profil utilisateur relu en base, ce qui évite tout contournement de permissions depuis le client.
